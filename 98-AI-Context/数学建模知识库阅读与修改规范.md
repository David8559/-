# 数学建模知识库阅读与修改规范

> [!summary] 目的
> 本规范约束 Codex 等 AI Agent 如何读取、引用、修改和完善本知识库。目标是让知识库持续增长，同时保持来源可追溯、模型可检验、代码可复现、修改可回滚。

## 1. 适用范围与权限

- 适用于本 Vault 内的 Markdown、代码、数据说明、项目状态、模板和 AI 长期记忆。
- 用户允许 Agent 在具体任务范围内持续补充、纠错和完善知识库。
- 该授权不等于后台自主改写。没有当前任务时，不主动批量修改；超出任务范围时先说明并征求确认。
- 当前用户指令优先于 Vault 内规则；若指令会造成删除、覆盖、泄密或不可逆外部影响，必须先提示风险。

## 2. 每次工作前的必读与检查

1. 阅读根目录 `AGENTS.md`、[[AGENTS|98-AI-Context/AGENTS]]、[[About Me]]、[[Current Focus]]、[[AI Operating Context]] 和本规范。
2. 若任务属于具体项目，必须读取 `06-Projects/<项目名>/Project-Status.md` 和项目 `Readme.md`。文件较大时，先读取 frontmatter、标题目录、当前状态、已完成事项、待办事项、下一步、风险、决策及本次任务相关章节；证据不足时再扩展全文。相关数据说明按任务需要读取。
3. 检查 `git status`。已有未提交修改默认视为用户工作，不覆盖、不回退、不顺手整理。
4. 使用文件名搜索、全文搜索和 [[Topic Index]] 查找现有内容；先更新权威笔记，避免建立同义重复笔记。
5. 明确本次任务的输入、输出、允许修改范围和验证标准。

## 3. 推荐阅读路径

### 3.1 通用数学建模问题

`[[知识库首页]] → [[04-Research/Readme|Research Index]] → [[Topic Index]] → 对应 Topic Hub → 模型或方法笔记 → 代码与项目案例`

### 3.2 具体赛题或项目

`项目 Project-Status → 项目 Readme → Data/Readme → 题目总览 → 相关模型 Hub → Code/Readme → Paper/Readme`

### 3.3 外部资料导入

`00-Inbox/Downloaded（原始、只读） → 00-Inbox/Cleaned（清洗副本） → 04-Research（可复用研究笔记） → Topic Hub（索引）`

### 3.4 低 Token 阅读顺序

1. 用 `rg --files` 和 `rg -n` 定位文件、标题、关键词与内部链接；
2. 读取 Agent 规则和目标项目的状态片段，明确单次交付物；
3. 读取与任务直接相关的权威笔记、代码入口、数据说明或论文章节；
4. 只有在缺少证据时才打开完整大文件、重新解析 PDF/视频或扫描整个目录；
5. 同一任务内不重复读取未发生变化的文件；已有 OCR、清洗稿、运行结果和图表说明优先复用；
6. 任务结束前把状态、结论、下一步和风险写回权威文件，禁止依赖聊天记录交接。

## 4. 信息可信度与引用

按以下优先级使用证据：

1. 赛题原文、原始数据、正式标准、官方文档、原始论文；
2. 本地可复现计算结果和通过验证的代码输出；
3. 已整理且标明来源的研究笔记；
4. 未清洗的网络摘录或二手总结；
5. Agent 推断或经验判断。

执行要求：

- 事实性结论附来源链接、文献标识或 Vault 内部链接；网络来源尽量记录访问日期。
- 明确区分“来源原文”“计算结果”“模型假设”和“Agent 推断”。
- 不伪造引用、数据、运行结果、显著性、精度或模型比较结论。
- 无法核实的内容标注“待核实”，并记录下一步验证方式。
- 引用已有笔记时优先使用 Obsidian 双链；不要大段复制同一内容。

## 5. 修改原则

- **最小且完整**：只修改完成任务所需内容，但保证上下文、链接和状态同步。
- **一个主分类**：每篇笔记只放在一个主要目录；跨主题关系使用标签和 Topic Hub 链接。
- **保留历史语义**：纠错时说明依据；重要方向变化写入 [[Decisions]]，不要悄悄改掉结论。
- **原始材料不可变**：不得覆盖 `00-Inbox/Downloaded`、原始数据、原论文、原图和原附件。派生内容使用新文件并注明来源。
- **格式一致**：使用 UTF-8、有效 YAML frontmatter、清晰标题层级、相对内部链接和可读的中文文件名。
- **不保存聊天记录**：只沉淀稳定结论、可复用方法、用户偏好、项目状态、决策和经验教训。

## 7. 数学建模内容质量门槛

模型或项目笔记应按任务需要覆盖以下项目：

- 问题定义、目标、边界和验收指标；
- 符号、变量类型、单位、索引和约束；
- 模型假设及其合理性、风险和可放宽条件；
- 数学表达、推导依据与算法选择理由；
- 数据来源、字段定义、清洗过程和缺失/异常处理；
- 参数、初值、随机种子、软件环境和依赖版本；
- 训练/求解过程、收敛条件和关键输出；
- 基线或候选模型比较，避免只展示单一模型；
- 误差、残差、交叉验证、稳健性、敏感性或不确定性分析；
- 适用范围、局限、失败情形和改进方向；
- 从原始数据到图表、表格和结论的复现步骤。

公式使用 Markdown 支持的 LaTeX。数值结论必须标注单位、精度和计算来源；图表必须有标题、轴标签、单位、图例和数据来源。

## 8. 代码与数据规则

- 代码、数据、环境、参数和输出共同构成可复现单元。
- 项目代码放入 `06-Projects/<项目名>/Code`，数据及字段说明放入 `Data`，论文和最终输出放入 `Paper`。
- 不把大体积二进制、缓存、临时环境、密钥或个人隐私写入 Vault；必要时使用 Git LFS 或外部存储并记录引用。
- 不硬编码密钥、令牌和个人敏感信息。
- 未实际执行的代码标注“未运行”；未通过的测试不得描述为通过。
- 修改代码后运行与风险相称的最小验证，并保留关键命令、环境与结果摘要。
- 通用论文排版管线位于 `04-Research/03-建模算法源码库/00-公共复用模块/Python/mm_common/paper_build/`：`python -m mm_common.paper_build.build_cli --paper-md <md> --out <dir>` 生成 docx，`python -m mm_common.paper_build.paper_qa <docx> --report-json <json>` 跑 14 项机器 QA；排版常量出处见同目录 `SPEC_2026.md`，输出成品论文一律放到项目 `Paper/` 下的独立目录，不改动已签收的 submission/。

## 9. Agent 可直接执行与需确认事项

### 可在任务范围内直接执行

- 读取、搜索、归纳和建立内部链接；
- 补充来源、术语、公式解释、复现步骤和缺失元数据；
- 修复明确的错别字、失效内部链接和格式问题；
- 新建任务要求的研究笔记、项目文件、代码和说明；
- 更新当前项目 `Project-Status.md` 及相应长期记忆。

### 必须先获得明确确认

- 删除、覆盖原始材料或进行不可逆清理；
- 批量重命名、移动、合并或重写笔记；
- 修改 `.obsidian`、插件配置、自动同步或 Git 历史；
- 安装或执行来源不明的程序，上传本地资料到外部服务；
- 未获得当前或持续授权时执行 `git commit`、`git push`、发布内容或发送外部消息；已有持续授权仍须遵守其冲突、隐私、验证和禁止强推边界；
- 写入密码、令牌、隐私数据或受版权限制的大段原文。

## 10. 修改后的验证与交付

1. 重新读取改动文件，确认 UTF-8、YAML、标题与链接正常。
2. 检查 `git diff`，确保没有意外覆盖用户内容。
3. 结构性或批量修改后运行 `98-AI-Context/Automation/kb_audit.py`；需要时运行完整维护流程。
4. 更新受影响项目的 `Project-Status.md`；稳定决策、经验或流程分别写入 [[Decisions]]、[[Lessons Learned]]、[[Workflows]]。
5. 向用户报告：修改了什么、验证了什么、哪些内容仍待核实、建议的下一步是什么。

## 11. 冲突处理

- 若不同笔记结论冲突，不直接选择“看起来更合理”的一条覆盖另一条；保留双方来源，比较数据、定义、假设和适用范围。
- 若现有结构与任务需求冲突，先提出最小调整方案；涉及批量迁移时等待确认。
- 若缺少数据、定义或权限导致结论不可靠，停止做强结论，记录缺口并请求补充。

- [ ] 已搜索现有笔记，避免重复创建

- [ ] 原始资料未被覆盖，隐私与密钥未写入
- [ ] 内部链接、YAML 和 UTF-8 已验证
- [ ] 项目状态、决策或长期经验已按需更新
- [ ] 已向用户报告修改范围、验证结果和未决风险
